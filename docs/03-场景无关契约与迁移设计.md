# 场景无关契约与迁移设计（三层契约）

**一句话**：把「任何行业、任何场景都能用」这个设计目的，落成**三层可替换契约**——换行业时只改词表与数据源，不改协议、不改编排、不改工具代码；并用一次真实的第二次迁移实测来证明它，而不是用文字声称。

**规则依据（逐字）**：
- 初赛评分第一项（25%）：「…模块解耦性、扩展性强，**适配多行业场景迭代需求**」
- 中国总决赛附加分（10 分）：「**多行业模板轻量化迁移适配验证**」

---

## 1. 三层契约

| 层 | 契约内容 | 换行业时**只改** | 状态 |
|---|---|---|---|
| **L1 MCP 工具契约** | 工具名、输入 schema、输出 schema、错误语义 | 数据源路径（环境变量） | ✅ 已实现（**两套**：`workbench` / `retrieval`，见 §2） |
| **L2 Skill 模板契约** | 步骤编排、模板字段名、失败语义 | 模板里的字段名与文案 | ✅ 已实现（**两个**模板，见 §3） |
| **L3 本体 schema 契约** | 实体/关系/属性的**类型系统**与更新规则 | 实例词表（term list） | ✅ **三层均已实现**（规则层 K1–K3 · 推理层 R1–R4 · 模型判定层；见 §4） |

> 判据：一次合格的迁移，**L1 与 L2 的代码行改动必须为 0**；若为改动 L1/L2 才能换行业，说明契约没抽干净，记一次契约缺陷。

---

## 2. L1：MCP 工具契约（已实现）

- 服务端：`mcp/workbench-mcp-server.py`（fastmcp 2.14.7，streamable-http `0.0.0.0:8791/mcp`，systemd 常驻）
- 三个工具的契约（与 `mcp/workbench-mcp.json` 逐字段一致）：

| 工具 | 入参 | 返回 |
|---|---|---|
| `workbench_task_status` | 无 | `{file, bytes, mtime, done, partial, todo}` |
| `workbench_recent_commits` | `limit: int = 5`（1–20） | `[string]` |
| `workbench_run_demo` | 无 | `{rc, seconds, model_calls, model_mode, domains}` |

- 行业无关性所在：三个工具的**输入输出 schema 里没有任何行业词**（没有「病历」「工单」「政策」字段），行业信息只出现在数据源内容与 Skill 模板文案里 ⇒ 换行业不需要改工具。
- 注册与发现证据：`POST /api/mcp/add` → `mcp_id=1`、`status:true`；`GET /api/tool/list` → `tool_id 34/35/36`（`usage:"workbench"`）；平台侧 `registry_json._toolNames` 与本地工具集合一致（说明是平台**连上去发现**的，不是我们手填的）。

**第二套 L1：`retrieval`（政务语料检索，2026-10-13 注册）**

- 服务端：`mcp/retrieval-mcp-server.py`（fastmcp，streamable-http `0.0.0.0:8793/mcp`，systemd 常驻）
- 契约（与 `mcp/retrieval-mcp.json` 逐字段一致）：

| 工具 | 入参 | 返回 |
|---|---|---|
| `retrieval_cross_doc` | `query: str, hops: int = 3, top_k: int = 5` | `{insufficient, max_score, chains[], levels[], date_range[]}` |
| `retrieval_trace_source` | `chunk_id: str` | `{found, text, title, date}` |
| `retrieval_corpus_stats` | 无 | `{indexed_docs, cleaned_docs, total_chunks, embedding{ok,dim}}` |

- **行业无关性所在（这一套更硬）**：三个工具的 schema 里没有任何行业词，也没有任何**行业字段名**——
  检索域完全由 `query` 文本决定，语料由索引决定；换行业只换索引与 `query`，**工具代码一行不改**。
- 注册与发现证据：`mcp_id=2`、`GET /api/tool/list` → `tool_id 38/39/40`（`usage:"retrieval"`）；
  扫描端点是 `GET /api/tool/scan_tool`（**POST 返回 405**，踩过一次）。

## 3. L2：Skill 模板契约（已实现）

- 模板：`skills/workbench-status-report/SKILL.md`（`skill_id=5`，`source=custom`）
- 契约要点：
  1. `allowed-tools` 声明 → 平台自动绑定到 MCP 工具（上传返回 `tool_ids:[34,35,36]`，未手工填 id）
  2. 步骤固定为 **取数 → 校验 → 成文**，任一步失败必须如实报告、禁止补全
  3. 成文模板的**字段名**是契约（`done/partial/todo/bytes/mtime/rc/seconds/model_calls/domains`），换行业只换这些字段的**取值来源**，不换步骤
- 运行证据：事件链 `read_skill_md` → `parallel_executor` → 三个 MCP 工具 → `final_answer`（按模板成文）。

**第二个 L2 模板：`governance-policy-trace`（政策法规检索与溯源）**

- 模板：`skills/governance-policy-trace/SKILL.md`；`allowed-tools` = `retrieval_cross_doc` / `retrieval_trace_source` / `retrieval_corpus_stats`
- 契约要点：
  1. 步骤固定为 **检索 → 判定证据充分性 → 回查原文 → 成文**，其中第 2 步是**拒答闸门**：
     `insufficient == true` 或 `max_score < 0.75` 或命中全部 `grounded == false` ⇒ 必须回答
     「语料库中没有找到足够依据」，**不得**用模型记忆补答；
  2. 第 3 步规定「回查失败（`found == false`）的环不得写进结论」⇒ 把「决策溯源」做成可执行约束；
  3. 成文模板的字段名（`结论 / 依据 / 制度沿革 / 引用块清单 / 数据来源`）是契约。
- **迁移判据**：换行业只改模板里的字段文案与 `query` 的领域词，不改步骤、不改工具名 ⇒ L2 改动行数应为 0。

## 4. L3：本体 schema 契约（✅ 三层均已实现：规则层 + 推理层 + 模型判定层）

**当前状态：三层均已实现并可复跑。** 产物在 `research/ontology/`，实测见
`research/236-ict-ontology.md`（规则层）、`237-ict-ontology-reasoning.md`（推理层）、
`238-ict-ontology-llm-judge.md`（模型判定层）、`239-ict-ontology-doc2doc.md`（双侧过滤全量）。

已落地的接口（即原设计草案）：

```
ontology/
  schema.json      # 类型系统：entity_types[] / relation_types[] / attribute_types[]
  terms.<行业>.zh.json  # 实例词表（换行业时只改这个文件）
  build.py         # 半自动构建：输入文档目录 → 输出 candidate 三元组（带置信度与出处）
  align.py         # 与行业规范/标准对齐：标准条款 ↔ 本体节点 的映射表
  reason.py        # 推理层：引用类谓词做有界传递闭包 + 逐环出处回查
  judge.py         # 模型判定层：逐条判定候选是否为真文件（零温度 + 缓存 + 入库前校验）
  prune.py         # 双侧过滤：只保留两端都被判为文件的引用边
```

- **行业无关性要求**：`schema.json` 的结构（键名与取值类型）必须与行业无关；行业只出现在 `terms.<行业>.zh.json` 的实例条目里（已实测：换词表时 `schema.json` 与 `build.py` 逐字节未变）。
- **验收判据（可复跑）与实测**：

| # | 判据 | 实测（2026-10-13 / 10-14） |
|---|---|---|
| K1 | `build.py` 输出的每条三元组都带出处（文件名 + 偏移） | 60,000 块 → **255,451 条**，`provenance_failed` **0** |
| K2 | 换行业时 `schema.json` 与 `build.py` 的**改动行数为 0** | 换制造词表后两文件 sha256 前后逐字节一致（`17a0455d…87b1` / `02c47bca…1e5b`）⇒ 改动行数 **0** |
| K3 | `align.py` 输出的映射表能反向查回标准原文位置 | 抽样 100 条 occurrence 回源复算 **100/100** |
| R1–R4 | 推理层判据：直接边不漏 / 传递性成立 / 无自环 / 每环带出处 | 全部通过，自测 5/5，全图 14,035 节点 / 148,005 边 / 闭包 171,552 对，3.8 秒 |

- **诚实边界**：判据三条全过，但**规则抽取不是 NER**（无模型、无标注集，召回率未测）；
  `medium`/`low` 候选按 `schema.json` 的 `review_gate` 需人工确认，**本轮一条都没有入库**；
  语料侧仍是**前 60,000 块子集**（全量 1,864,451 块）；推理层**深度天花板 3 跳**，
  且第 3 跳开始掺正文短语（已由模型判定层量化，见 §7）。

## 5. 迁移改动清单（模板见 `04-迁移改动清单模板.md`）

一次迁移实测必须记录四个数字（这是「轻量化」的唯一客观证据）：

| 指标 | 定义 | 目标 |
|---|---|---|
| L1 改动行数 | 迁移前后 `workbench-mcp-server.py` 的 diff 行数 | **0** |
| L2 改动行数 | `SKILL.md` 的 diff 行数 | 只允许改模板文案/字段来源 |
| 迁移工时 | 从「拿到新行业 20 份文档」到「跑出第一份简报」的墙钟时间 | 越小越好（记录实测值） |
| 复用率 | 复用文件数 / 总文件数 | 越高越好 |
