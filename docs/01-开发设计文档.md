## 1. 作品定位与赛题对应

### 1.1 一句话定位

「个人 AI 工作台」是一套**可离线自持的多 Agent 开发与验证链**（Electron 桌面端 + Python 运行时 +
元框架调度层）。**作品核心是检索–推理链与本体构建流程，工作台不是主体，而是「能力沉淀与
可迁移性」的佐证**：它把自己的真实运行数据（任务对账、提交历史、演示链健康度）通过
**自建 MCP 服务**暴露给 Nexent，再由**自建 Skill 工作流模板**约束智能体「取数 → 校验 → 成文」，
让智能体的回答从「凭模型记忆」变成「可逐字段复核的事实」。它的价值不在于「也是我们做的」，
而在于**证明同一套方法在另一个平台上也能落地**（同一套判据、同一套本体格式、同一个 MCP 协议）。

## 2. 业务价值与目标用户

**问题**：多 Agent 开发链的产出（计划、对账表、提交、演示链）散落在文档与日志里。人问「现在到哪了」，
智能体往往凭上下文记忆作答，**数字对不对无法当场判断**——这正是「AI 说得像真的」的典型风险。

**做法**：把工作台的**真实工程状态**做成 MCP 工具，再用 Skill 把「必须取数、必须校验、必须标注来源」
固化成流程约束。

**目标用户**：① 需要向他人（老师/队友/评审）证明工程真实进度的开发者；② 需要把内部系统能力
暴露给智能体、又不允许智能体自由编造的企业场景（该 Skill 模板与 MCP 骨架可直接替换业务字段复用）。

**可观测价值**：智能体回答中的每个数字都能追溯到「哪个工具、哪个文件、多少字节、什么时候」。

**分层理由**：Nexent 负责「编排、模型、技能、工具注册」；工作台负责「真实业务数据与执行」；
两者之间**只有一条明确的契约**——MCP 工具的三个函数签名。任何一方内部重构都不会破坏集成，
这是可维护性的关键。

### 4.3 Skill 工作流模板设计（自建，赛题三第二半）

`skills/workbench-status-report/SKILL.md`（52 行，sha256 = `e174e05c92b7228018670fe363940c5535a5dccda6089e3bf7846548758c80c3`）：

```yaml
name: workbench-status-report
allowed-tools: [workbench_task_status, workbench_recent_commits, workbench_run_demo]
tags: [workbench, mcp, report]
```

正文规定 **四步流程**：① 取数（依次调用三工具）→ ② 校验（逐字段与工具原始返回对照，
不符则**不得写入简报**，改报「该字段未取到」）→ ③ 按模板成文 → ④ 标注数据来源（工具名 + 文件 + 字节数）。
模板中**强制**包含两条诚实约束：计数口径说明、`model_mode` 是否为真实模型。

**为什么这样设计**：把「不许编造」从人的口头要求，变成**技能文本里的可执行约束**——
这是本作品在 Skill 层面的核心创新点（见 §6）。

**第二个 Skill 模板：`skills/governance-policy-trace/SKILL.md`（59 行）**

```yaml
name: governance-policy-trace
allowed-tools: [retrieval_cross_doc, retrieval_trace_source, retrieval_corpus_stats]
tags: [retrieval, governance, traceability, mcp]
```

正文规定**四步流程**：① 检索（`retrieval_cross_doc`）→ ② **判定证据充分性**（`insufficient == true`
或 `max_score < 0.75` 或命中全部 `grounded == false` ⇒ 必须回答「语料库中没有找到足够依据」，
不得用模型记忆补答）→ ③ **回查**（对每一环调 `retrieval_trace_source`；`found == false` 的环不得写进结论）
→ ④ 成文（模板含「制度沿革」与「引用块清单」）。

它把**拒答闸门**与**决策溯源**写成技能文本里的可执行步骤——这两件事最容易在演示时被模型「顺着说下去」，
写进 Skill 才能在每次运行时都生效。

### 4.4 「检索-推理」双驱动执行流

实测一次调用（`evidence/04-custom-skill-report.sse.log`）的事件顺序：

```
other(uncertainty_reserve_active, uncertainty_reserve_tokens=100000, effective_input_limit_tokens=995904)
  → agent_new_run → step_count
  → tool(search_memory)                     ← 检索驱动 ①：平台记忆
  → tool(read_skill_md)                     ← 技能注入：读自建技能正文
  → tool(parallel_executor)                 ← 编排：并行取数
  → tool(workbench_task_status)             ← 检索驱动 ②：MCP 取真实数据
  → tool(workbench_recent_commits)
  → tool(workbench_run_demo)
  → model_attempt_control(begin) → model_output_thinking → token_count → commit   ← 推理驱动
  → final_answer
```

**双驱动**的判定标准：回答中的每个事实字段，都能在**工具事件**里找到同值来源；
若某字段只有模型输出、没有工具事件支撑，即视为「单驱动（纯推理）」而不合格。

**MCP 驱动版实测（2026-10-13，`evidence/06-agent-cross-doc.sse.log`）**：
提问「市场准入负面清单制度是哪一年建立的？地方有哪些落实文件？」触发 **17 次工具调用**
（`retrieval_cross_doc` ×7 + `retrieval_trace_source` ×10）、耗时 **54.3 s**、答案 **7,525 字符**，
引用以 `[[a1]]` 形式标注到具体块。事件链：

```
step_count → tool(retrieval_cross_doc) ×7        ← 检索驱动：多跳取数
  → tool(retrieval_trace_source) ×10             ← 出处回查：逐条回原文
  → model_attempt_control(begin) → model_output_thinking → token_count → commit   ← 推理驱动
  → final_answer（含引用块清单：chunk_id + 标题 + 日期）
```

**拒答同样是「双驱动」的证据**：负例（问「量子计算芯片的光刻胶配方工艺参数」）**只调用 1 次工具、
15.7 s** 即明确回答「语料库中没有找到足够依据」——没有工具支撑的结论一律不写，这正是本节判定标准
在运行时的体现（证据 `evidence/07-agent-insufficient.sse.log`）。

### 4.5 知识图谱构建方案（三层**均已实现**：规则层 + 推理层 + 模型判定层）

**现状声明（先说清楚）**：本作品的 L3 本体是**三层分工**，三层都已落地且可复跑：
**① 规则层**——`ontology/schema.json`（类型系统）、`ontology/terms.<行业>.zh.json`（行业词表）、
`ontology/build.py`（抽取引擎）、`ontology/align.py`（规范名归并与反向查回），
已在 60,000 块语料上跑出 **188,423 条三元组**（出处校验失败 0）与 **116,958 个规范实体**；
**② 推理层**——`ontology/reason.py` 把引用类谓词连成有向图做有界传递闭包，
**强证据层 2,827 节点 / 7,009 边 / 闭包 7,117 对，0.3 秒**（全量口径 14,035 / 148,005 / 171,552，3.8 秒），判据 R1–R4 全过；

`ontology/prune.py` 据此做双侧过滤。
对应三层契约的 L3（详见 `03-场景无关契约与迁移设计.md` §4）。

**设计要点**

1. **分层（行业无关性）**：`schema.json`（类型系统：entity_types / relation_types / attribute_types，结构与行业无关）
   / `terms.<行业>.zh.json`（实例词表，**换行业只改这个文件**——已实测换制造词表时 `schema.json` 与 `build.py` 的 sha256 逐字节未变）。
2. **低资源半自动构建（三段式）**：
   ① 规则与结构抽取——标准条款编号、表格表头、文档层级 → 高置信候选；
   ② 小样本提示补召回——每类实体 ≤10 个示例，避免大样本依赖；
   ③ 人工确认闸门——候选必须**带出处**（文件名 + 偏移），无出处不入库。
3. **与行业规范/标准对齐**：`align.py` 产出「标准条款 ↔ 本体节点」映射表，且能反向查回原文位置。
4. **持续动态更新**：三类更新事件（新增实体 / 关系冲突 / 条目废弃）由「重跑 `build.py` 产出 diff + `align.py` 归并同名实体」落地；
   产物按日期留档、旧版本可回滚（本仓 `ontology/` 下已有三元组产物与判定缓存的分代留存）。
5. **与智能体的接口**：本体以 **MCP 工具**形式暴露（如 `query_ontology` / `get_entity` / `trace_source`），
   智能体经 MCP 调用 ⇒ **本体层不侵入 L1 契约**（这是 L1 行业无关性的关键）。

**推理半边（引用链，`ontology/reason.py`）**

抽取出的三元组是散点；把它们按引用类谓词（`cites`/`implements`/`amends`/`repeals`）连成有向图，
做有界传递闭包（从每个节点 BFS，深度上限 4），再逐环取回出处，就得到「谁引用了谁」的链条。
它与 retrieval MCP 的多跳检索分工明确：**多跳检索走向量相似度，答「像不像」；本体推理走显式引用边，答「谁引用了谁」**。

| 置信度门槛 | 节点 | 边 | 1 跳 | 2 跳 | 3 跳 |
|---|---|---|---|---|---|
| 全量（strict+候选层） | 14,035 | 148,005 | 148,005 | 20,671 | 2,876 |
| **强证据层（strict）** | **2,827** | **7,009** | **7,009** | **106** | **2** |
| medium 及以上 | 12,718 | 109,240 | 120,724 | 11,324 | 160 |
| **仅 high（strict）** | **2,827** | **7,009** | **7,117** | **106** | **2** |

判据 R1–R4 全过（直接边不漏 / 传递性成立 / 无自环 / 最长链逐环带出处），自测 5/5，全图 3.8 秒。

**两个必须写明的读数**：① **深度天花板是 3 跳**——`--max-depth` 放到 5 也没有第 4 跳，与政务文件「国家 → 省 → 市」三级体系一致；
② **长链几乎全靠候选层撑**——2 跳链从 11,324（medium+）掉到 106（strict），−99%；3 跳链从 160 掉到 2，−99%，
因为 high 门槛只保留「强后缀 + 专有标记」的文档名。**规则层的引用链可信到 2 跳，第 3 跳开始掺短语**
（如把「环境标准」「与之相伴的全球经贸规则」这类正文短语判成文件）——要提纯长链需要的不是更复杂的正则，而是判定能力。

**诚实边界**：闭包是**有界**的（起点全图、深度 4），不是数学意义的完全传递闭包；3 跳天花板是本语料子集（60,000 块）的读数，不是政务文件体系的普遍结论；第 3 跳掺短语，**不应当直接拿去做「制度依据」的对外表述**。

**模型判定层（`ontology/judge.py`）**

规则层用后缀 + 前缀 + 长度门槛判文档名，能判对强后缀的（《…条例》），
但判不出「环境标准」「与之相伴的全球经贸规则」这类**形态像文件名的正文短语**——这不是再堆正则能解的。
所以补第三层，三层分工写死：**规则管召回、模型管判定、人工闸门管入库**。

判定器把一批 20 条候选发给模型（零温度），要求返回 `{"i","is_doc","reason"}`，带缓存（同候选不重复调用）与入库前校验（`is_doc` 必须布尔、`reason` 必须非空）。支持 `--candidates-file` 直接吃上游剪枝清单（逐行去重保序），缓存逐批落盘（中断不丢）。自测 6/6。

各判 400 个候选的实测：

| 侧 | 候选 | 判为文件 | 占比 |
|---|---|---|---|
| object（被引用者） | 400 | 35 | **8.8%** |
| subject（引用者） | 400 | 6 | **1.5%** |

**subject 侧噪音比 object 侧严重 6 倍**——因为这个语料以媒体报道为主：媒体报道会**提到**法规（object 侧有真文件），但媒体报道自己不是文件（subject 侧几乎全是新闻/会议标题）。

**全量双侧过滤读数**（`prune.py`，四谓词全边 202,553 条）：过滤前 202,553 条边 / 119,258 节点 →
只清 object 侧 24,495 条 → 只清 subject 侧 65,199 条 → **双侧都清 15,870 条 / 8,532 节点**。
对这批文件→文件边跑引用链：1,661 节点 / 9,167 边 / 闭包 9,335 对 / 最大深度 **3 跳**（2 跳 159 · 3 跳 9），
多跳边只占 **1.8%** ⇒ 文件→文件图**浅而宽**（谓词分布 `cites` 11,706 · `implements` 2,659 · `amends` 986 · `repeals` 519）。

**这一处必须写明修正**：早先基于「object 与 subject 各 400 个候选」的抽样曾得出「双侧都清 0 条」，
并据此推断「政务文件之间的显式引用链比想象中稀疏得多」。**全量判定推翻了后一句**：
两端都是文件的边有 **15,870 条**，稀疏的不是边，是**链的深度**（多跳边仅占 1.8%）。
抽样错在**层**——那 400 个 subject 候选里只有 6 个真文件（1.5%）、400 个 object 里只有 35 个（8.8%），
从噪音占九成的池子里随机抽，6×35 的组合里恰好一条边都没有。
**正确做法是先从已确认为文件的节点出发再往外走**（全量读数与复跑命令见 `239-ict-ontology-doc2doc.md`）。

**诚实边界**：判定用外部模型（自备网关 `deepseek-v4.1-flash`，零温度），换模型结论可能变；模型判定有错（`根据国际刑事司法协助法的规定` 被判为文件，实为句子片段）；判定结果只作过滤视图，**未改写 `236` 的三元组产物**，`review_gate` 之后仍无一条人工确认入库；object 侧全量 31,934 条候选实测 **63 分钟**跑完（`--workers 8`；网关侧约 2 条/秒是瓶颈，16 并发反而更慢）。

**增量更新（对应官方要求的「本体持续动态更新」）**

本体不是一次性产物，但也不是「每来一批新文件就全量重跑」。当前实现是**两段式增量**：

1. **语料增量** —— `tools/subset-incremental.py` 按关键词与时间窗从全量语料里抽新块，只抽没抽过的（以 `doc_id` 去重）。
2. **三元组增量** —— `tools/merge-triples.py` 把新块跑 `build.py` 得到的增量三元组合并进已有本体：
   读已有三元组建 `{(subject, predicate, object): 记录}` 索引 → 读增量 → 严格去重 → 输出合并结果 + 统计
   （`added` / `duplicates_skipped` / `affected_entities` / `added_by_predicate`）。

**端到端实测**：500 个新块 → `build.py` 抽出 705 条 → 合并进已有 12,594 条强证据层：
**新增 606 / 重复跳过 99 / 受影响实体 429**。

**设计取舍（必须一起读）**：只做**严格去重** —— 同名实体的不同表述不模糊合并（模糊合并会把「北京市」和「北京市人民政府」并成一个，
而这两者在政务语境里是不同的主体）；新记录的 `review_status` **原样保留**，不把待人工的洗成自动的；
`affected_entities` 本身是一条判据 —— 新增只触及少数实体，说明新语料与已有本体几乎无交集；反之则说明重复抽取严重。

3. **第三条路：直接从网上抓**（2026-10-19 新增）—— `tools/live-ingest.py` 给 URL 或列表页，走「抓取 → 切块 → 抽三元组 → 增量合并」全程：
   - 支持 HTML 正文（`<p>` 段落）与 `.pdf`（`pymupdf` 逐页 `get_text()`，覆盖有文本层的政府 PDF）
   - `--from-index https://www.gov.cn/zhengce/xxgk/` 从 209 KB 静态 HTML 里自动抽出 50 个 `content_*.htm` 链接（带标题），无需 JS 渲染
   - **实测**：列表页取 10 篇 → 34 块 → 强证据层 28 条 / 候选层 270 条 → 合并新增 298 条（受影响实体 258）
   - **边界**：`/zhengce/pdf/` 404、`gongbao/2024/` 403（公报子页反爬）；扫描件走 OCR（`rapidocr-onnxruntime` 1.4.4 已装，切片后可用）；
     走 HTTP 代理会超时，代码里用 `ProxyHandler({})` 强制直连；`--from-index` 的正则按 gov.cn 写的，换站点要改

**还没做的**：增量更新目前是**手动两段**（先跑语料增量、再跑三元组合并），没有调度器；
也没有「删除」路径 —— 如果上游撤回一份文件，已抽出的三元组不会自动消失。

**标准体系映射（对应官方要求的「与行业规范/标准体系对齐」）**

本体自身的 5 类实体与 8 个关系是行业无关的抽象，但它们不是自造概念 —— `ontology/standard-mapping.json`
把它们逐个映射到两个公开的通用词汇表：

| 本体 | Schema.org | W3C PROV-O | 对应程度 |
|---|---|---|---|
| Document | `CreativeWork` / `Legislation` | `prov:Entity` | 部分（「通知/意见/办法」不在 Legislation 下） |
| Organization | `Organization` / `GovernmentOrganization` | `prov:Agent` | 完全 |
| Region | `AdministrativeArea` / `Place` | — | 完全 |
| TimePoint | `Date` / `DateTime` | `prov:generatedAtTime` | 部分（不覆盖「施行时间」） |
| Concept | `DefinedTerm` | — | 完全 |
| cites | `citation` | `prov:wasDerivedFrom` | 完全 |
| implements | `isBasedOn` | `prov:wasInfluencedBy` | 部分（不隐含「下位」方向） |
| amends | — | `prov:wasRevisionOf` | 部分（Schema.org 无对应属性） |
| repeals | — | `prov:wasInvalidatedBy` | 部分（方向相反，需实现层翻转） |
| issued_by | `publisher` / `author` | `prov:wasAttributedTo` | 完全 |
| effective_from | `validFrom` | `prov:generatedAtTime` | 部分（必须选 validFrom，不是 datePublished） |
| applies_to | `spatialCoverage` | — | 完全 |
| mentions | `mentions` | — | 完全 |

**5 类实体 + 8 个关系中：7 项 exact、6 项 partial、2 项在词汇表里无对应（属本体自定义扩展）。**

**为什么映射到 Schema.org 与 PROV-O 而不是国标**：这两个词汇表是**公开可查**的（`schema.org`、`w3.org/TR/prov-o`），
评委可当场打开核对；而政务国标（如《政务信息资源目录体系》）的原文我们**没有拿到**，硬写条款号等于编造。
**这是「概念来源可追溯」，不是「已通过标准认证」** —— 两件事的强度不同，答辩时不能混。

**校验**：`python3 tools/check-standard-mapping.py` 检查四件事 —— schema 的每个实体/关系都有映射、
映射里没有 schema 不认识的 id、每条映射至少指向一个词汇表、`summary` 声明的数字与实际统计一致。
**自测 7/7**（含六种畸形输入：删映射、拼错 id、词汇表全空、summary 数字不符、coverage 非法）。

**跨文档推理与决策溯源（演示，2026-10-13）**

## 5. 关键技术决策与理由

| 决策 | 备选 | 理由（可验证） |
|---|---|---|
| MCP 用 **streamable-http**（`/mcp`）而非 SSE | `/sse` | 平台按 URL 后缀判定传输：以 `/sse` 结尾 → sse，否则 streamable-http（`backend/agents/create_agent_info.py:2889`）；http 端点单连接、更少握手 |
| MCP 服务**跑在宿主机**而非容器内 | 打进 Nexent 容器 | 工作台是宿主目录与宿主进程，容器内需再挂载且失去 systemd 自愈；宿主 + 桥地址最简且可独立重启 |
| 技能**自建**而非只用官方技能 | 只用官方 4 个 | 赛题三要求「沉淀可复用模板」；官方技能不含本作品的业务约束 |
| 计数**如实标注口径** | 直接写「已完成 94 项」 | 94 是标记出现次数（表内 77）；错报口径在复核时会被抓，且违背可复现性要求 |
| 用 `uv run --with fastmcp` 起服务 | pip 全局安装 | 宿主 Python 3.10 与 fastmcp 依赖存在冲突风险；`uv` 已装且能精确锁 2.14.7（与容器内版本一致，避免协议行为差异） |
| 参赛版**独立目录** `/home/endmin/project-ict` | 直接用自用版 | 自用版有个人运行数据；参赛版需开源（GitCode/GitHub），必须可公开 |

## 6. 创新性

1. **把「真实工程状态」变成 MCP 契约**：不是演示型 mock 工具，而是读取真实文档字节数、
   mtime、`git log` 与真实演示链退出码——智能体的每句话都落在可复核的事实上。
2. **技能即校验规则（Skill as contract）**：`SKILL.md` 不只写「怎么做」，还写「什么情况下**必须报失败**」
   （字段缺失不得补全、`rc != 0` 不得粉饰）。实测该约束生效：智能体在简报中主动补了
   「口径说明」与「`model_mode=offline_fixture_NOT_live_LLM`，非真实大模型调用」两条限定。
3. **双向自持闭环**：工作台产出数据 → 自建 MCP 暴露 → Nexent 编排 → 自建 Skill 约束 → 回到工作台验证。
   两侧都是自己的代码，端到端可调试、可定位（对比「只能用平台内置能力」的集成深度差异）。
4. **可复现性作为一等公民**：本作品的验证文化是「有判据 ≠ 判据在跑」——判据必须挂在真会被执行的命令上，
   且必须能抓到**已经发生过**的 bug（本项目自建的 X17 断言集、成本归因 A1–A7、MCP 探针均由此而来）。
5. **判据的设计方法论来自自建元框架**：本作品的四个关键判据不是凭直觉加的，而是由作者自建的 7 站元框架
   流水线（`127.0.0.1:8101`）的四条原则导出的 —— `adversary`（把契约自己的字面量往旁边推一格，看生成物
   会不会当场塌）对应 `verify_quote` 的 16 条对抗用例；`audit`（每条结论必须带出处）对应每个环带
   `chunk_id` + `asset_id`；`arena`（同一句话几个候选各答一遍，摆在一起看）对应三个工具并列而不是一个
   万能工具；`advisory`（LLM 建议不能覆盖实测值或执行判定）对应 `review_gate` 只放行人工确认过的。
   **这四条是设计工具，不是运行时依赖** —— 元框架本身不参与演示链路，但它决定了判据长什么样。

| 7 | 写块时 embedding 服务收到空串（日志 `input_preview=['','','']`），平台报 `500 … 400 Bad Request for url: …/v1/embeddings` | 我的导入器把正文字段写成 `text`，平台读的是 `item.get("content","")`（`management/services/knowledge_base/management.py:1090`） | 字段名改 `content` ⇒ `Successfully indexed 3 documents` |
| 8 | 3 进程并发导入全部失败：`HTTP 500 … Read timed out. (read timeout=20.0)` | 平台侧对 embedding 的读超时 20 s，并发争抢 CPU 后每批超阈值即整批失败 | 改单进程串行（本机 embedding 单条 0.09 s，瓶颈在平台侧不在向量化） |

---

- **UI 里「智能体消失」的根因不是权限，是 `connect_status`**：API 能列出智能体、UI 却显示「共 0 个智能体」。
  逐层查下来是前端用 `/api/agent/published_list`（不是 `/api/agent/list`）且按 `is_available` 过滤，
  而 `is_available` 取决于模型 `connect_status == "available"`；新注册模型默认 `not_detected`，
  必须跑一次平台自己的 `POST /api/model/healthcheck?display_name=...&model_type=...` 才会变成 `available`。
  教训：**「接口有数据」不等于「界面有数据」，中间还隔着一层可用性判定**。
- **CDP 自动化的三个必踩坑**：① Chrome 以 403 拒绝来自 `http://127.0.0.1:9222` origin 的 WebSocket，
  客户端需 `suppress_origin=True`；② 从 WSL 调 Windows exe 要写成 `.bat` 再 `cmd.exe /c`；
  ③ 脚本被 timeout 杀掉时若没加 `python3 -u`，会一行日志都不留（stdout 缓冲）。
